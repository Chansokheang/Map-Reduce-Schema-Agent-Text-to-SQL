3. PROPOSED METHOD (2-3 pages)
================================================================================

3.1 System Overview
- Two-phase architecture diagram (reference proposed_method.png)
- Phase 1: Map-Reduce Schema Agent
- Phase 2: SQL Selection Agent

3.2 Phase 1: Map-Reduce Schema Agent

    3.2.1 Agentic Decomposition (The Manager)
    - Input: Natural language query
    - Process: LLM-based semantic parsing
    - Output: Query components
      * [entity] - main data entity (e.g., "members", "schools")
      * [filter] - filtering conditions (e.g., "in Alameda County")
      * [aggregation] - operations (e.g., "highest", "count")
      * [projection] - output fields (e.g., "zip code", "phone")
    - Example decomposition (include figure)

    3.2.2 Mapping Function (Parallel Workers)
    - One worker per table (parallel execution)
    - Each worker: mini-LLM for relevance scoring
    - Relevance Coefficient (RC): 0.0 to 1.0
    - Scoring criteria:
      * Table name semantic match
      * Column name/description match
      * Query component alignment
    - Discretization: RC → {1.0, 0.5, 0.0}

    3.2.3 Reduce Function (Ranking & Filtering)
    - Collect all RC scores from workers
    - Apply threshold filter (RC >= 0.50)
    - Sort tables by relevance descending
    - Output: Focused Schema

3.3 Phase 2: SQL Selection Agent

    3.3.1 Context-Aware Generation (5 Strategies)

    | ID | Strategy        | Context Description                    |
    |----|-----------------|----------------------------------------|
    | Q1 | Full Schema     | Complete database schema, no hints     |
    | Q2 | SME Metadata    | Schema + evidence from domain experts  |
    | Q3 | Minimal Profile | Schema + auto-generated descriptions   |
    | Q4 | Focused Schema  | Relevant tables only (from Phase 1)    |
    | Q5 | Full Profile    | Focused schema + descriptions + hints  |

    - Rationale for each strategy
    - Prompt templates (system + user prompts)
    - Parallel generation for efficiency

    3.3.2 Execution & Iterative Refinement
    - Execute each candidate SQL against database
    - If error: LLM refines SQL with error feedback
    - Max 3 iterations per candidate
    - Success criteria: executes without error + returns results
    - Rejection: 3 failed attempts → mark as rejected

    3.3.3 Last Resort Mechanism
    - Triggered when ALL 5 candidates fail
    - Uses failed attempts as negative examples
    - Generates one final corrected SQL
    - Prevents complete pipeline failure

    3.3.4 LLM-as-a-Judge Selection
    - Role: Senior SQL Reviewer
    - Input: Successful candidates only
    - Evaluation criteria:
      * Correctness: Does SQL answer the question?
      * Completeness: All required information returned?
      * Efficiency: Proper JOINs, no redundant operations?
      * Logic: Correct filtering and aggregation?
    - Output: Selected SQL + confidence score + reasoning

3.4 Implementation Details
- LLM model: Claude (Sonnet/Haiku)
- Parallelization: ThreadPoolExecutor
- Database: SQLite (BIRD format)
- Timeout: 30 seconds per query
- Threshold: RC >= 0.50
